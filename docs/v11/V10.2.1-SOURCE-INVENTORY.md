## Current deploy pipeline that v11 must preserve

The current scripts implement, among other checks:

- immutable releases;
- source SHA-256 binding to the built image;
- exclusive deployment lock;
- source audit before deployment;
- Docker/Compose validation;
- migration rehearsal on a clone of production DB;
- pre-deploy backup;
- candidate app health check before public exposure;
- SQL schema and rollback-compatibility checks;
- internal smoke tests;
- security-header and CSRF smoke tests;
- Caddy/HTTPS activation only after candidate health;
- production HTTPS smoke test;
- runtime pointers committed only after all gates are green;
- automatic pre-public and post-public recovery paths;
- client wrapper confirmation of `DEPLOY PASS`, `PRODUCTION AUDIT PASS`, and an external `https://gomaf.online/healthz` check.

## Existing rollback constraint

The deployment code already supports forward-compatible rollback after public exposure by keeping the migrated DB and starting the previous immutable release with Flyway disabled while Hibernate schema validation remains enabled.

This behavior is a key enabler for the v10.2.1 -> v11 transition. New v11 migrations used before legacy removal must therefore be additive/forward-compatible with the v10.2.1 entity model unless a maintenance-only migration explicitly changes the rollback contract.
